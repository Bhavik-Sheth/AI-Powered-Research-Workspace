# Notes — Design & Architecture

`backend/notes/` is a two-function read module: it lists a project's notes and flags which ones
have no `idea_edges` link. It owns no writes and no table of its own — the `notes` table is
created and mutated entirely by `backend/vault/` (Vault Writer), and full-text indexing of a
note's body into memory is a separate job triggered from `backend/api/notes.py`, not from this
module. `notes/` exists purely to keep the routes from running raw SQL for the reads Vault
Writer's public surface doesn't cover.

---

## Storage / data model

`notes/` defines no models or tables itself. It reads the `Notes` ORM row (`db/models.py:121-152`)
and returns the wire-shape `Note` pydantic model (`vault/models.py:31-54`).

`Notes` table shape (`db/models.py:121`):
- `id` (UUID PK) — generated by Vault Writer at note-creation time, written into the note file's
  own YAML frontmatter, never derived from `file_path`.
- `project_id` (FK → `projects.id`, cascade delete).
- `title`, `file_path`, `body` (all `String`, not null).
- `frontmatter` (JSONB, defaults to `{}`).
- `created_at`, `updated_at` (`updated_at` has `onupdate=func.now()`; `eager_defaults=True` on the
  mapper so an UPDATE's new `updated_at` comes back via `RETURNING` instead of a lazy reload).
- Unique constraint on `(project_id, file_path)`.

`notes/__init__.py` also reads `IdeaEdges` (`db/models.py`, imported at `notes/__init__.py:16`) to
compute unlinked notes — no new table, just a join-free two-query check against an existing one.

## Core mechanics

### Read path — this module's actual code

`list_notes(session, project_id)` (`notes/__init__.py:20-25`): one `SELECT` on `Notes` filtered by
`project_id`, ordered `updated_at DESC`, mapped to `Note.from_row` for each. Backs the notes list
view.

`list_unlinked_note_ids(session, project_id)` (`notes/__init__.py:28-49`): two queries, no SQL join.
1. Selects all `Notes.id` for the project; returns `[]` immediately if there are none.
2. Selects `(src_id, dst_id)` from `IdeaEdges` where `project_id` matches and either `src_type` or
   `dst_type` is `"note"`.
3. In Python, flattens the edge endpoints into a set, intersects with the note-id set, and returns
   every note id **not** in that intersection.

This is a correctness-relevant nuance worth flagging: step 3 intersects *all* edge endpoints
(source and destination combined, regardless of type) against the note-id set — it does not check
that the specific endpoint referencing a given id was actually typed `"note"` at that position. In
practice this is safe only because ids are UUIDs (a `"paper"`-typed edge endpoint could not
collide with a note's id), not because the query logic itself distinguishes edge endpoint type
from row type.

### Where notes are actually created/edited — not this module

Writing happens entirely in `vault.write_note` (`vault/__init__.py:76-130`), invoked from
`api/notes.py:28` (POST, create) and `api/notes.py:43` (PATCH, update):
- Create: no `frontmatter_id` on the `NoteInput` → new UUID generated, a unique
  `projects/<slug>/notes/<slug>.md` path is chosen (`vault/__init__.py:61-73`, appending `-2`,
  `-3`, … on collision), the markdown file (YAML frontmatter + body) is written to that path, then
  a new `Notes` row is inserted in the same DB transaction the route's `db.session()` commits.
- Update: `frontmatter_id` present → the existing row is loaded, `file_path` and `id` never move,
  only `title`/`body`/`frontmatter` are overwritten in place, file and row updated together.
- If the file write succeeds but the DB flush fails, `VaultWriteFailed` is raised and the file is
  left as an accepted orphan on disk — `vault/__init__.py:36` documents there is no reconciliation
  pass; the caller's `db.session()` rolls the DB side back but the file stays.

### Relationship to memory indexing

Only the **create** route enqueues indexing: `api/notes.py:33` calls
`jobs.enqueue("chunk_and_embed_job", source_type="note", source_id=str(note.id))` right after
`vault.write_note` returns. The **update/PATCH** route (`api/notes.py:37-47`) does not enqueue
anything — an edited note's body is never re-chunked or re-embedded, so memory search only ever
reflects a note's state as of its first save.

`chunk_and_embed_job` (`memory/__init__.py:145-161`) dispatches `source_type="note"` to
`_chunk_note` (`memory/__init__.py:96-113`): re-fetches the `Notes` row by id, splits `body` into
spans via `split_span`, embeds each span, and inserts one `ProjectChunks` row per span with
`source_type="note"`. As `memory/__init__.py:147` notes in its own docstring, re-running this job
for the same note id just appends duplicate chunk rows — there is no delete-then-reinsert, which
compounds the "update never re-enqueues" gap: an edited note can't be fixed up even by manually
re-triggering the job without first cleaning up the stale rows.

## Callers & dependents

Both public functions in `notes/__init__.py` are called from live paths:

- `notes.list_notes` — `api/notes.py:19` (`GET /api/projects/{project_id}/notes`, the notes list
  endpoint) and `api/projects.py:129` (the project dashboard's `get_dashboard` route, which pulls
  the full note list to build stat/feed data).
- `notes.list_unlinked_note_ids` — `api/projects.py:130`, same dashboard route, backing the
  "N unlinked" tile qualifier.

No dead code was found inside `notes/__init__.py` itself — both its functions are reached. The
dead/partial paths sit downstream, in the modules it depends on and the route that fronts it:

- `api/notes.py`'s PATCH route never calls `jobs.enqueue(...)` — a real, live gap: edits to a
  note's body silently never reach memory.
- `_chunk_note`'s caller path (`chunk_and_embed_job` with `source_type="note"`) is otherwise live
  and reachable only via `api/notes.py:33`'s create route — there is no other enqueue site for
  notes anywhere in the codebase (confirmed by grep).

## Open questions / rough edges

- **Stale memory on edit.** As above: `PATCH /api/projects/{project_id}/notes` updates the note's
  file and DB row but never re-triggers `chunk_and_embed_job`. A note's searchable memory content
  is frozen at first-save time, and there's no way to catch it up short of manual intervention —
  and manual re-enqueue would itself just append duplicate `ProjectChunks` rows rather than
  replace the stale ones, since no re-indexing path exists (`memory/__init__.py:147`).
- **Unlinked-note check doesn't verify endpoint type.** `list_unlinked_note_ids`
  (`notes/__init__.py:28-49`) treats any `IdeaEdges` endpoint (`src_id` or `dst_id`) whose value
  matches a note id as "linked," without checking that `src_type`/`dst_type` at that position was
  actually `"note"`. It happens to be correct today because ids are UUIDs and collisions across
  entity types are effectively impossible, but the code does not enforce or assert this — it's an
  implicit invariant, not a checked one.
- **Module docstring flags its own scope gap.** `notes/__init__.py:1-9` explicitly notes that
  MODULES.md's Vault Writer interface only names `write_note`, and that this module exists to fill
  the read-side gap "flagged here for the same reason, not added silently" — i.e., the split
  between `vault/` (writes) and `notes/` (reads) is a deliberate, documented workaround for a
  narrower originally-specified interface, not an organic architectural boundary.
- **No delete path anywhere.** Neither `notes/__init__.py` nor `vault/__init__.py` nor
  `api/notes.py` defines any note-deletion function or route — notes can only be created and
  updated, never removed, in the current code.
